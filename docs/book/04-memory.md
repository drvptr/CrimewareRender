# 04. Память: арена вместо malloc

Файлы `core/arena.h` и `core/arena.c`. Сорок строк кода и одно решение,
которое определяет вид всех загрузчиков.

## Что такое арена

Арена — это кусок памяти и число, сколько от него уже занято.

```c
struct arena {
	char *base;   /* начало куска */
	long size;    /* сколько всего */
	long used;    /* сколько занято */
	long peak;    /* максимум, которого достигали */
	int failed;   /* было ли переполнение */
};
```

Выделение — прибавление к `used`:

```c
void *
arena_Alloc(struct arena *a, long bytes, long align)
{
	start = a->used;
	while (start % align != 0)
		start++;

	if (start + bytes > a->size) {
		a->failed = 1;
		return 0;
	}

	p = a->base + start;
	for (i = 0; i < bytes; i++)
		p[i] = 0;

	a->used = start + bytes;
	return p;
}
```

Всё. Ни списка свободных блоков, ни заголовков перед блоками, ни поиска
подходящего места. Такой аллокатор называется bump allocator — «толкающий»,
потому что он просто двигает указатель вперёд.

Освобождения по одному блоку нет вообще. Освобождается всё сразу:

```c
long mark = arena_Mark(&a);    /* запомнили, где были */
load_level(&a);                /* сотни выделений */
arena_Reset(&a, mark);         /* уровня больше нет */
```

`arena_Reset` — это `a->used = mark`. Одна инструкция освобождает мегабайты.

## Почему не malloc

Не потому, что `malloc` плох. Потому, что игре он не нужен, а его
отсутствие даёт четыре вещи.

**Нет утечек.** Утечка — это забытый `free`. Здесь нет `free`, забывать
нечего. Худшее, что может случиться, — арена кончится, и это видно сразу
по `failed`, а не через два часа игры.

**Нет фрагментации.** Классическая беда игр: загрузили уровень, выгрузили,
загрузили следующий, и память изрешечена дырами так, что большой
непрерывный кусок уже не выделяется. Арена не фрагментируется по
построению.

**Скорость.** `malloc` в многопоточной программе — это блокировка, поиск и
кэш-промахи. Арена — сложение. Загрузка модели на 8540 вершин делает тысячи
выделений и не замечает их.

**Никакой libc.** Движок без `malloc` — это движок, который можно собрать
`-nostdlib` и запустить там, где libc нет вообще. Твоя `buf/buffer.c` уже
такая; арена делает такими и загрузчики.

Плата тоже настоящая: нельзя освободить один объект в середине. Для игры
это не проблема — уровень живёт целиком и умирает целиком, — но если
понадобится удалять отдельные объекты, придётся заводить для них
собственный пул со списком свободных ячеек.

## Зачем выравнивание

Третий аргумент `arena_Alloc` — выравнивание.

```c
float *v = arena_Alloc(&a, n * sizeof(float), 4);
```

Процессор читает четырёхбайтовое число быстрее, если его адрес кратен
четырём; на некоторых архитектурах (ARM старых версий, MIPS) невыровненное
чтение — это не «медленнее», а аварийное завершение. Поэтому арена по
запросу подвигает начало блока вперёд до кратного адреса.

Правило простое: выравнивание не меньше размера самого большого поля в
типе. Для `float` и `int` — 4, для `double` и указателей — 8, для байтов —
1.

## Почему память приходит обнулённой

```c
	for (i = 0; i < bytes; i++)
		p[i] = 0;
```

Это стоит времени, и его можно было бы сэкономить. Не экономим осознанно:
неинициализированная память — источник ошибок, которые воспроизводятся
через раз. Обнулённая структура сразу корректна, потому что во всём движке
ноль значит «ничего»: нулевой дескриптор текстуры, пустой список, нулевой
счётчик.

Если когда-нибудь загрузка станет заметно долгой, обнуление — первое, что
можно выключить флагом. Пока это не проблема: демо занимает 815 КБ и
загружается мгновенно.

## Паттерн mark/reset

Основной приём работы с ареной. Встречается в `game_init` дважды.

```c
	mark = arena_Mark(&g->mem);

	bytes = slurp(&g->mem, "wall.tga", &len);        /* временное */
	pixels = arena_Alloc(&g->mem, size, 4);          /* временное */
	tga_Decode(pixels, size, bytes, len);
	g->wall_tex = gfx_MakeTexture(pixels, geo, 1, 1);/* результат уехал в GPU */

	arena_Reset(&g->mem, mark);                      /* всё временное исчезло */
```

Читать так: «всё, что я выделю между `Mark` и `Reset`, — черновик».

Ограничение — стековый порядок. Освободить можно только то, что было
выделено позже. Нельзя выделить A, потом B, потом освободить A, оставив B.

## Как обойти стековый порядок

В `obj_Parse` эта проблема встаёт в полный рост, и решение стоит разобрать
— это самый неочевидный кусок работы с памятью во всём движке.

Задача: разобрать `.obj`. Нужны временные массивы (позиции, координаты
текстуры, нормали, хеш-таблица) и постоянные (вершины, индексы, таблица
источников). Постоянные должны пережить временные, а размер вершин заранее
неизвестен — известна только верхняя граница.

Решение — порядок выделения:

```c
	out->index = arena_Alloc(a, ntri * 3 * sizeof(unsigned short), 2);
	verts_offset = arena_Mark(a);
	out->verts = arena_Alloc(a, ntri * 3 * sizeof(struct gfx_vertex), 4);
	out->source = arena_Alloc(a, ntri * 3 * sizeof(int), 4);

	b.pos = arena_Alloc(a, ...);      /* дальше только временное */
	b.uv = arena_Alloc(a, ...);
	b.table = arena_Alloc(a, ...);
```

Индексы первыми, потому что их количество известно точно. Вершины вторыми
по верхней границе. Временное — сверху, чтобы его можно было срезать.

После разбора известно настоящее `nverts`, и происходит вот что:

```c
	at = verts_offset + out->nverts * sizeof(struct gfx_vertex);
	while (at % 4 != 0)
		at++;
	packed = (int *)(void *)(a->base + at);
	for (i = 0; i < out->nverts; i++)
		packed[i] = out->source[i];
	out->source = packed;
	arena_Reset(a, at + out->nverts * sizeof(int));
```

Таблица источников переезжает вниз, вплотную к реальному концу массива
вершин, и арена обрезается сразу за ней. Одним движением исчезают и все
временные массивы, и неиспользованный хвост массива вершин. Потерь ноль.

Копирование безопасно при перекрытии, потому что назначение всегда ниже
источника, а цикл идёт вперёд: каждый байт читается раньше, чем его успеют
затереть.

## Сколько памяти на самом деле нужно

```c
	printf("demo: arena %ld of %ld bytes used\n", g->mem.used, g->mem.size);
```

Демо: 815 КБ из 48 МБ. Пул выбран с запасом, потому что статический массив
ничего не стоит, пока в него не пишут: система выделяет физические
страницы по факту обращения.

`peak` — максимум, до которого арена доходила, включая уже откаченные
черновики. Именно его надо смотреть, подбирая размер пула: `used` покажет
только то, что осталось.

## Проверки

В `test/test.c` арена проверяется целиком:

```c
	check(((char *)q - block) % 16 == 0, "alignment is honoured");
	check(arena_Mark(&a) == mark, "reset returns to the mark");
	check(arena_Alloc(&a, 1000000, 1) == 0, "a full arena returns 0");
	check(a.failed == 1, "and remembers that it failed");
```

Последняя проверка — про то, что флаг `failed` липкий. Загрузчик делает
десяток выделений подряд и не проверяет каждое: если хоть одно не влезло,
флаг останется, и достаточно одной проверки в конце.

```c
	if (a->failed)
		return -1;
```

Так код загрузчика остаётся читаемым, а не превращается в лестницу из
`if (p == 0) goto fail`.
