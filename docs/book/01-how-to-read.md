# 01. Как читать этот код

Прежде чем открывать первый файл, полезно знать соглашения. Они
выдержаны везде, поэтому, узнав их один раз, дальше можно читать быстро.

## Каталоги

```
buf/      геометрия буфера: как байты превращаются в «картинку 640x480»
core/     математика, память, главный цикл
plat/     операционная система: окно, ввод, время, звуковое устройство
gfx/      рисование треугольников
asset/    разбор форматов файлов
world/    секторы, порталы, коллизии
snd/      микшер
ui/       интерфейс и катсцены
demo/     пример игры
test/     проверки
tools/    вспомогательные скрипты, запускаются руками
docs/     документация
```

Правило зависимостей: стрелки идут только вниз по этому списку. `world/`
может включать `core/`, но `core/` никогда не включает `world/`. Взаимных
включений нет ни одного. Это не педантизм: именно поэтому можно взять
`core/m3.c` и вставить в другой проект, ничего не потащив за собой.

## Пара «заголовок и .c»

Каждый модуль — это два файла: `foo.h` и `foo.c`.

`.h` — это договор. В нём написано, что модуль умеет, и ничего про то,
как. Читать надо его. Комментарии в заголовках оформлены как мини-мануал:

```c
int coll_RayAabb(struct vec3 origin, struct vec3 dir, const struct aabb *b,
    float *t_out);
/* USAGE:
	if (coll_RayAabb(eye, direction, &box, &t)) ...
   RETURN VALUE:
	1 при попадании, 0 при промахе
   NOTE:
	t_out (можно 0) получает расстояние до ближней грани
*/
```

`USAGE` — как звать. `RETURN VALUE` — что вернётся. `NOTE` — то, что
неочевидно и о чём иначе споткнёшься.

`.c` — реализация. Её читать нужно, только когда что-то ведёт себя не так,
как обещал заголовок, или когда интересно почему.

## Именование

Каждая публичная функция начинается с имени модуля:

```
plat_OpenWindow    plat/    открыть окно
gfx_DrawMesh       gfx/     нарисовать меш
obj_Parse          asset/   разобрать .obj
wld_Visible        world/   какие секторы видны
coll_MoveAabb      world/   подвинуть коробку с коллизиями
snd_Play           snd/     проиграть звук
gui_Button         ui/      кнопка
cut_Start          ui/      запустить катсцену
arena_Alloc        core/    отрезать памяти
app_Run            core/    запустить игру
```

Увидев `wld_` в чужом коде, сразу знаешь, что искать в `world/world.h`.
Функции без префикса — статические, живут внутри одного `.c` и наружу не
видны.

Математика — исключение: `v3_add`, `m4_mul`, `fr_test_aabb`. Она
встречается в каждой второй строке, и длинные имена там мешали бы читать.

Второе исключение там же: векторные функции определены прямо в `m3.h` как
`static inline`, а не в `.c`. Причина измерена и расписана в главе 06 —
коротко, вызов такой функции через границу файла стоит в восемь раз
дороже, чем её тело.

## Стиль

Тип возвращаемого значения стоит на отдельной строке перед именем
функции:

```c
struct vec3
v3_add(struct vec3 a, struct vec3 b)
{
	return v3(a.x + b.x, a.y + b.y, a.z + b.z);
}
```

Так `grep '^v3_add' *.c` находит определение, а не вызовы. Это стиль ядра
BSD, и он же в твоём старом коде.

Отступы — табуляции. Переменные объявляются в начале функции, а не по
месту. Никаких `typedef` на встроенные типы: в коде написано `unsigned
long long` и `int`, а не `u64` и `i32`. Никаких трюковых макросов: если
надо проверить условие, стоит обычный `if`.

## Дескрипторы вместо указателей

Текстура и меш возвращаются как число:

```c
unsigned int tex = gfx_MakeTexture(pixels, geo, 1, 1);
unsigned int mesh = gfx_MakeMesh(verts, nverts, index, nindex, 0);
```

Это не указатель. Это номер, по которому рендер найдёт всё, что нужно,
внутри себя. Такая штука называется непрозрачным дескриптором (opaque
handle).

Зачем: игра физически не может залезть внутрь и что-нибудь испортить, а
рендер волен хранить хоть номер объекта OpenGL, хоть индекс в своём
массиве. `gfx_null.c` (пустой рендер для тестов) просто выдаёт возрастающий
счётчик, и игра не замечает разницы.

**Ноль всегда значит «ничего».** Нулевая текстура — «без текстуры», и меш
нарисуется однотонным. Нулевой меш — «нечего рисовать», и функция тихо
выйдет. Поэтому свежая обнулённая структура игры сразу корректна, и не надо
писать конструкторы.

## Коды возврата

Три семейства, перепутать трудно:

- функции разбора возвращают `0` при успехе и `-1` при ошибке
  (`obj_Parse`, `tga_Decode`, `wav_Parse`);
- функции-вопросы возвращают `1` (да) и `0` (нет) (`coll_AabbAabb`,
  `tga_Probe`, `fr_test_aabb`);
- функции-конструкторы возвращают дескриптор или `0`.

`errno` нет, глобального состояния ошибок нет. Функция, у которой нет
состояния, переживает и потоки, и прерывания, и повторный вызов.

## Аргументы

Устойчивый порядок: сначала куда пишем, потом откуда читаем, потом
размеры, потом настройки.

```c
int tga_Decode(void *dst, long dstcap, const void *data, long len);
```

`dstcap` — это ёмкость назначения, и она обязательна. Функция, которая
пишет в чужую память, не имея права спросить, сколько её там, — это
переполнение буфера, ждущее своего часа. Здесь такого нет ни в одном
загрузчике.

Указатель, помеченный `const`, функция только читает. Указатель с
суффиксом `_out` — необязательный, туда положат результат, можно передать
`0`, если не нужен.

## Что такое `struct arena *` в половине сигнатур

Это память, из которой загрузчику разрешено брать. Подробно в главе 04.
Пока достаточно: движок не зовёт `malloc`, поэтому память ему передают
явно, как и всё остальное.

## Сборка

```sh
make            # демо: X11 + OpenGL          -> ./demo-bin
make check      # тесты, дисплей не нужен     -> ./test-bin
make PLAT=null GFX=null   # демо вообще без окна
make freestanding         # доказать, что buf/ ничего не импортирует
make clean
```

Две переменные, `PLAT` и `GFX`, выбирают, какие файлы бэкендов положить в
сборку. Никакой системы сборки, никаких конфигураторов: `make` вызывает
`cc` со списком файлов. Весь движок компилируется меньше чем за секунду,
поэтому объектные файлы и инкрементальная сборка не нужны.

Обрати внимание, чего нет в строке компоновки:

```
cc ... -lm -lX11 -ldl
```

Ни `-lGL`, ни `-lasound`. OpenGL и ALSA открываются во время работы через
`dlopen`, поэтому бинарник запускается и на машине, где их нет. Как это
устроено — глава 05.

## Куда смотреть, когда что-то сломалось

| симптом | куда |
|---|---|
| не собирается | `Makefile`, список файлов вверху |
| собралось, ничего не нарисовалось | `gfx/gfx_gl.c`, строка `gfx:` в выводе при старте |
| проваливается сквозь пол | `world/coll.c`, `coll_MoveAabb` |
| видно то, чего не должно | `world/world.c`, `wld_Visible` |
| модель вывернута наизнанку | обход вершин, глава 07, раздел про отсечение |
| тишина | `plat_AudioOpen` вернул 0, звукового устройства нет |
| съело всю память | `g->mem.peak`, глава 04 |
