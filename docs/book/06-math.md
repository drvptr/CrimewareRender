# 06. Математика

Файлы `core/m3.h` и `core/m3.c`. Три сущности: вектор, матрица 4×4,
фрустум. Всё на `float`, потому что видеокарта работает с `float` и любая
попытка сэкономить на фиксированной точке кончится преобразованием обратно.

## Вектор

```c
struct vec3 {
	float x;
	float y;
	float z;
};
```

Вектор здесь значит две разные вещи, и это стоит различать:

- **точка**: где что-то находится. Позиция игрока, угол комнаты;
- **направление**: куда что-то смотрит. Взгляд камеры, нормаль
  поверхности, скорость.

Тип один, различие в голове программиста. Оно всплывёт при умножении на
матрицу: точку надо двигать вместе с миром, направление — нет.

### Что делают операции

`v3_add`, `v3_sub`, `v3_scale` — покомпонентно, очевидно.

**Скалярное произведение** `v3_dot(a, b)` = `ax*bx + ay*by + az*bz`. Одно
число. Для векторов единичной длины оно равно косинусу угла между ними:

```
1    смотрят одинаково
0    перпендикулярны
-1   смотрят навстречу
```

Отсюда всё освещение: `dot(нормаль, к_свету)` — насколько поверхность
повёрнута к источнику. Отсюда же панорама звука: `dot(на_источник, вправо)`
— справа он или слева.

**Векторное произведение** `v3_cross(a, b)` даёт вектор, перпендикулярный
обоим. Порядок важен: `cross(a, b)` и `cross(b, a)` смотрят в
противоположные стороны. Отсюда нормаль треугольника: взять два его ребра и
перемножить.

**Длина** `v3_len` — теорема Пифагора в трёх измерениях. **Нормализация**
`v3_norm` делает длину единичной, сохраняя направление:

```c
struct vec3
v3_norm(struct vec3 a)
{
	len = v3_len(a);
	if (len < 0.000001f)
		return v3(0.0f, 0.0f, 0.0f);
	return v3_scale(a, 1.0f / len);
}
```

Проверка на почти-ноль обязательна: без неё нулевой вектор даёт деление на
ноль и `NaN`, а `NaN` расползается по всем последующим вычислениям, и
объект просто исчезает с экрана без единого сообщения об ошибке.

Нормализовать нужно всё, что участвует в `dot` как направление, иначе
косинус выйдет за пределы от -1 до 1 и освещение станет неправильным.

## Почему векторные функции лежат в заголовке

Все `v3_*` определены прямо в `m3.h` как `static inline`. Это не стиль, а
измеренное решение, и стоит понимать, откуда оно взялось.

Структура из трёх `float` весит 12 байт и по System V ABI (x86-64) не
передаётся через память вообще — она **режется между двумя регистрами
XMM**: `{x, y}` в один, `{z}` в другой. Само тело функции от этого
получается идеальным:

```asm
v3_add:
	addss	xmm1, xmm3
	addps	xmm0, xmm2
	ret
```

Две инструкции, ни одного обращения к памяти. Но платит за это место
вызова, потому что в памяти вектор лежит тремя подряд идущими числами, а в
регистрах должен оказаться разрезанным:

```asm
call_struct:
	movss	xmm1, DWORD PTR A[rip+8]
	movq	xmm0, QWORD PTR A[rip]
	movq	xmm2, QWORD PTR B[rip]
	movss	xmm3, DWORD PTR B[rip+8]
	call	v3_add
	movq	QWORD PTR C[rip], xmm0
	movss	DWORD PTR C[rip+8], xmm1
```

Шесть обращений к памяти вокруг функции, которая делает три сложения.

Замеры на одной задаче (нормаль треугольника и освещение, 2 млн точек,
`gcc -O2`), когда вызов идёт через границу единицы трансляции:

| как | время | отношение |
|---|---|---|
| `struct` по значению, в `m3.c` | 0.90 s | 8.0x |
| `float[3]` по указателю, в `m3.c` | 0.35 s | 3.1x |
| `struct` по указателю, в `m3.c` | 0.60 s | 5.4x |
| `struct` по значению, `static inline` в `m3.h` | 0.11 s | 1.0x |

Вариант с `float[3]` действительно быстрее, чем вызов структуры по
значению — интуиция «тут что-то тратится зря» верна. Но он в три раза
медленнее правильного ответа, потому что борется с соглашением о вызове
вместо того, чтобы убрать вызов.

Заодно `float[3]` стоил бы всего стиля записи. Массив в C нельзя вернуть из
функции и нельзя присвоить:

```c
typedef float vec3[3];

vec3 v3_add(vec3 a, vec3 b);   /* error: declared as function returning an array */
b = a;                         /* error: assignment to expression with array type */
```

То есть `n = v3_norm(v3_cross(e1, e2))` пришлось бы писать тремя
операторами с временными переменными, и так везде.

Матрицы при этом живут наоборот: `float[16]` по указателю, тела в `m3.c`.
64 байта не помещаются в регистры ни при каком ABI, а `m4_mul` с тремя
вложенными циклами встраивать незачем. Правило — размер, а не вкус.

Побочный эффект от `static inline` в заголовке: в отладочной сборке
(`-O0`) каждая единица трансляции получит свою копию функции и вызовы
останутся настоящими. На размер релизного бинарника это не влияет.

## Система координат

Y вверх, X вправо, Z на зрителя. Правая тройка, как в OpenGL.

```
      +Y (вверх)
       |
       |
       +------ +X (вправо)
      /
    +Z (на зрителя)
```

Из этого следует, что камера по умолчанию смотрит в **минус** Z. Это видно
в `m4_fps_view`:

```c
	dir.x = cosf(pitch) * sinf(yaw);
	dir.y = sinf(pitch);
	dir.z = -cosf(pitch) * cosf(yaw);
```

При `yaw = 0` и `pitch = 0` направление равно `(0, 0, -1)`.

Blender работает в Z-вверх, поэтому экспортёр переводит `(x, y, z)` в
`(x, z, -y)`. Если модель из другого места лежит на боку — почти наверняка
причина в этом.

## Матрица 4×4

```c
float m[16];
```

Не структура, а массив из шестнадцати чисел, потому что именно в таком виде
его ждёт OpenGL: `glUniformMatrix4fv` получает указатель и копирует
шестнадцать `float`. Структура потребовала бы `.m` при каждом вызове и
ничего бы не дала.

### Column-major

Порядок хранения — по столбцам:

```
	m[0] m[4] m[8]  m[12]
	m[1] m[5] m[9]  m[13]
	m[2] m[6] m[10] m[14]
	m[3] m[7] m[11] m[15]
```

То есть первые четыре числа — первый **столбец**, а не первая строка.
Так исторически устроен OpenGL, и следование этому соглашению избавляет от
транспонирования при каждой передаче.

Практическое следствие: перенос лежит в `m[12]`, `m[13]`, `m[14]`.

```c
void
m4_translate(float out[16], float x, float y, float z)
{
	m4_identity(out);
	out[12] = x;
	out[13] = y;
	out[14] = z;
}
```

Если однажды всё поедет вбок или картинка вывернется, первое подозрение —
перепутанный порядок; в матрицах это самая частая ошибка.

### Что делает умножение

Матрица 4×4 описывает преобразование: поворот, масштаб, перенос или их
комбинацию. Умножение матриц склеивает преобразования в одно.

Порядок обратный порядку применения. Строка

```c
	m4_mul(model, move, model);   /* model = move * model */
```

значит «сначала то, что было в model, потом move». Читать такие цепочки
надо справа налево. В демо:

```c
	m4_rot_y(spin, g->model_spin);
	m4_scale(scale, 0.004f, 0.004f, 0.004f);
	m4_translate(move, 0.0f, 1.2f, 0.0f);
	m4_mul(model, spin, scale);    /* сначала уменьшить, потом повернуть */
	m4_mul(model, move, model);    /* и только потом сдвинуть вверх */
```

Если поменять местами масштаб и перенос, модель сдвинется на 1.2, а потом
это смещение тоже уменьшится в 250 раз, и она окажется у самого пола.

Реализация умножения складывает результат во временный массив:

```c
	float t[16];
	...
	m4_copy(out, t);
```

Без этого вызов `m4_mul(a, a, b)` затирал бы входные данные по ходу
вычисления. С временным массивом любая комбинация одинаковых аргументов
работает.

## Три матрицы кадра

**Model** переводит из системы координат объекта в мировую. У каждого
объекта своя.

**View** переводит из мировой в систему координат камеры. Одна на кадр. Это
обратная матрица положения камеры: чтобы камера сдвинулась вправо, весь мир
надо сдвинуть влево.

**Projection** переводит из координат камеры в экранные и создаёт
перспективу.

Всё вместе:

```c
	m4_mul(mvp, cur_viewproj, model);   /* proj * view * model */
```

и шейдер делает одно умножение на вершину:

```glsl
	vec4 clip = u_mvp * vec4(a_pos, 1.0);
```

## Перспектива

```c
void
m4_perspective(float out[16], float fov_y_radians, float aspect,
    float near_z, float far_z)
{
	f = 1.0f / tanf(fov_y_radians * 0.5f);
	out[0] = f / aspect;
	out[5] = f;
	out[10] = (far_z + near_z) / (near_z - far_z);
	out[11] = -1.0f;
	out[14] = (2.0f * far_z * near_z) / (near_z - far_z);
}
```

Ключевая строка — `out[11] = -1.0f`. Она кладёт в четвёртую компоненту
результата (`w`) расстояние до камеры. Видеокарта потом делит x, y и z на
`w`, и это деление и есть перспектива: дальнее становится мельче.

Побочная польза: `clip.w` — готовое расстояние до камеры, и туман в шейдере
считается из него бесплатно.

`fov_y` — вертикальный угол обзора в радианах. 1.2 радиана — примерно 69
градусов, стандарт для игр от первого лица.

`aspect` — отношение ширины окна к высоте. Забудешь пересчитать при
изменении размера окна — картинка растянется.

`near_z` и `far_z` — ближняя и дальняя плоскости отсечения. Ближе `near_z` и
дальше `far_z` не рисуется ничего. Соблазн поставить `near_z = 0.001`, чтобы
не отсекалось лишнее, надо давить: точность буфера глубины распределена
между ними неравномерно, почти вся уходит на ближнюю область, и при
маленьком `near_z` далёкие поверхности начнут мерцать, проваливаясь друг
сквозь друга (это называется z-fighting). Разумная пара — 0.1 и 200.

## Камера

Две функции на выбор.

```c
	m4_look_at(view, eye, at, up);            /* смотреть на точку */
	m4_fps_view(view, eye, yaw, pitch);       /* смотреть по углам */
```

`m4_look_at` строит систему координат камеры из трёх векторов:

```c
	f = v3_norm(v3_sub(at, eye));    /* вперёд */
	s = v3_norm(v3_cross(f, up));    /* вправо */
	u = v3_cross(s, f);              /* вверх, уже перпендикулярный */
```

`up` — подсказка «где верх», обычно `(0,1,0)`. Она не обязана быть точно
перпендикулярной взгляду, поэтому настоящий верх пересчитывается через
второе векторное произведение.

Особый случай: если смотреть строго вверх, `f` совпадёт с `up`, векторное
произведение даст ноль, и камера сойдёт с ума. Поэтому в демо угол
ограничен:

```c
	g->pitch = m3_clampf(g->pitch, -1.5f, 1.5f);
```

1.5 радиана — чуть меньше 90 градусов.

## Фрустум

Фрустум — это объём, который видит камера: усечённая пирамида, ограниченная
шестью плоскостями (левой, правой, нижней, верхней, ближней, дальней).

Нужен для отбраковки: если объект целиком вне фрустума, его нет смысла
отправлять на видеокарту.

```c
struct frustum {
	float p[6][4];
};
```

Каждая плоскость — четыре числа `a, b, c, d`, задающие уравнение
`a*x + b*y + c*z + d = 0`. Точка внутри, если результат положительный.

Извлекаются они прямо из матрицы (метод Гриббa и Хартманна):

```c
	for (i = 0; i < 4; i++) {
		f->p[0][i] = m[i * 4 + 3] + m[i * 4 + 0];   /* левая */
		f->p[1][i] = m[i * 4 + 3] - m[i * 4 + 0];   /* правая */
		...
	}
```

Магия здесь только кажущаяся: точка видна, если после умножения на матрицу
её координаты укладываются в `-w <= x <= w`. Расписав это неравенство, ровно
и получаешь сумму и разность строк матрицы.

Затем плоскости нормализуются, чтобы `a*x+b*y+c*z+d` давало настоящее
расстояние в метрах, а не пропорциональное ему число. Для «внутри или нет»
это неважно, для проверки сферы (`fr_test_sphere` сравнивает расстояние с
радиусом) — обязательно.

### Проверка коробки

```c
	for (i = 0; i < 6; i++) {
		px = f->p[i][0] >= 0.0f ? max[0] : min[0];
		py = f->p[i][1] >= 0.0f ? max[1] : min[1];
		pz = f->p[i][2] >= 0.0f ? max[2] : min[2];
		if (f->p[i][0] * px + f->p[i][1] * py + f->p[i][2] * pz +
		    f->p[i][3] < 0.0f)
			return 0;
	}
	return 1;
```

Наивно надо было бы проверить все восемь углов коробки против всех шести
плоскостей — 48 вычислений. Здесь для каждой плоскости выбирается **один**
угол: тот, что дальше всех в сторону, куда смотрит нормаль плоскости. Если
даже он оказался снаружи, то и вся коробка снаружи. Шесть вычислений вместо
сорока восьми.

Функция может ошибиться в безопасную сторону: изредка скажет «видно» про
коробку, которой не видно (в углу между двумя плоскостями). Это стоит
одного лишнего вызова отрисовки. Обратной ошибки — сказать «не видно» про
видимое — она не делает никогда, а именно та была бы заметна как исчезающие
стены.

## Обращение матрицы

`m4_invert` — единственная длинная функция в файле, сто строк
алгебраических выражений. Это разложение по минорам, выписанное вручную:
для матрицы 4×4 это быстрее любого общего алгоритма и не требует ветвлений.

В движке она сейчас не используется, а в тестах проверяется тождеством
`M * M⁻¹ = I`. Понадобится, как только нужно будет перевести клик мыши в луч
в мире (обратить viewproj) или посчитать нормаль при неравномерном
масштабировании.
