# 02. `main()`: от запуска до первого кадра

Открываем `demo/main.c` и идём сверху вниз.

## Точка входа

```c
int
main(void)
{
	static struct game g;
	struct app_hooks hooks;

	hooks.title = "engine demo";
	hooks.width = 1024;
	hooks.height = 640;
	hooks.step_hz = 60.0f;
	hooks.max_fps = 250;
	hooks.audio_rate = 44100;
	hooks.init = game_init;
	hooks.step = game_step;
	hooks.draw = game_draw;
	hooks.quit = game_quit;
	hooks.user = &g;

	return app_Run(&hooks);
}
```

Вся игра — это четыре функции и указатель на своё состояние. Больше `main`
не делает ничего.

### Почему `static struct game g`

`struct game` содержит массивы и может весить десятки килобайт. Обычная
локальная переменная живёт в стеке, а стек по умолчанию 8 МБ, и его легко
переполнить. `static` кладёт структуру в статическую память программы,
рядом с глобальными переменными, и стек не трогает. Плюс `static`
гарантирует, что всё поле обнулено при старте, а ноль у нас везде значит
«ничего» (глава 01).

### Что такое хук

Хук (hook) — это указатель на функцию, которую движок вызовет в нужный
момент. Движок не знает, что такое «игра», зато знает, что в определённый
момент надо позвать `hooks->step`. Это называется инверсией управления: не
ты зовёшь библиотеку, а библиотека зовёт тебя.

Четыре хука:

| хук | когда зовётся | что там пишут |
|---|---|---|
| `init` | один раз, после создания окна | загрузка ресурсов, постройка уровня |
| `step` | ровно 60 раз в секунду | вся логика: движение, ИИ, столкновения |
| `draw` | раз в кадр, сколько успеет | только рисование |
| `quit` | один раз перед выходом | сохранение, освобождение чужих ресурсов |

`hooks.user` — указатель, который движок протащит через все четыре хука, не
заглядывая внутрь. Это способ передать своё состояние, не заводя
глобальных переменных. Внутри каждого хука первая строка одинаковая:

```c
static void
game_step(void *user, float dt)
{
	struct game *g;

	g = (struct game *)user;
```

### Почему `step` и `draw` — разные функции

Логика должна идти строго 60 раз в секунду независимо от того, рисует ли
машина 30 кадров или 300. Если считать движение по времени кадра, то на
быстрой машине прыжок получится другой высоты, чем на медленной, а
коллизии перестанут воспроизводиться. Подробно — глава 03.

Правило: в `step` нет ни одного вызова `gfx_*`, в `draw` нет ни одного
изменения игрового состояния. Нарушить его технически можно, и всё будет
как будто работать, пока кто-нибудь не запустит игру на другом железе.

## `struct game`: состояние мира

```c
struct game {
	struct arena mem;
	struct world world;

	unsigned int room_mesh;
	unsigned int wall_tex;

	struct obj_mesh model;
	unsigned int model_mesh;

	struct unit unit[UNITS];
	int controlled;

	struct camera cam;
	struct vec3 map_focus;
	int mouse_look;
};
```

Одна плоская структура без указателей на кучу. Это не случайность: такое
состояние сохраняется на диск одним `write()` и загружается одним `read()`,
без сериализации. Как только в игре появятся указатели друг на друга,
сохранения превратятся в отдельную подсистему.

### Три разные вещи, которые нельзя складывать в одну

```c
struct unit {              /* кто ходит по уровню, их несколько */
	struct vec3 pos;
	struct vec3 velocity;
	float yaw;
	int on_floor;
	int has_order;
	struct vec3 order;
	float colour[4];
};

struct camera {            /* откуда смотрим, живёт в demo/camera.c */
	int mode;
	float yaw, pitch;
	float distance;
	float eye_height;
	struct vec3 target;
	struct vec3 pos;
};

int controlled;            /* кем управляют прямо сейчас, просто индекс */
```

В первой версии этого файла позиции камеры и персонажа были **одной**
переменной по имени `eye`, и в книге было написано «позиция камеры, она же
позиция игрока». Это работало, демка была от первого лица — и это была
ошибка, потому что демка это шаблон, который копируют. Вместе с ней
копировалось бы предположение «камера в глазах, персонаж один».

Движок такого предположения не содержит нигде, и это можно проверить
грепом:

```sh
grep -rn "camera\|player" core/ gfx/ world/ plat/ snd/ --include=*.h
```

Найдётся `gfx_SetCamera(view, proj)`, который принимает две готовые
матрицы, и `m4_fps_view()` в математике — удобная функция рядом с
`m4_look_at()`, а не требование. Всё, что движок знает про то, откуда
смотрят:

```c
void gfx_SetCamera(const float view[16], const float proj[16]);
int  wld_Visible(const struct world *w, int from, const float viewproj[16],
                 int *out, int max);
void snd_Listener(struct vec3 position, struct vec3 forward);
```

Матрица, номер сектора, точка. Откуда они взялись, движка не касается: из
глаз персонажа, из точки над полем боя, с рельсов катсцены, из камеры
наблюдения на стене.

### Что даёт разделение на практике

Три режима в демке переключаются клавишами 1, 2, 3 и отличаются двумя
числами:

| режим | поводок | наклон | точка интереса |
|---|---|---|---|
| `CAM_FIRST` | 0 | ±1.5 | подопечный |
| `CAM_THIRD` | 4 м | от -1.2 до 0.6 | подопечный |
| `CAM_TOP` | 18 м | от -1.4 до -0.3 | свободная точка на карте |

Первое лицо — это третье лицо с нулевым поводком, а вид сверху — с длинным
и с точкой интереса, которая ни к кому не привязана. Один код в
`demo/camera.c`, тридцать строк.

TAB переключает, кем управляют. В виде сверху WASD ведут камеру, а пробел
отдаёт выбранному приказ идти в ту точку, над которой она висит, — и он
идёт туда сам, тем же кодом столкновений. Управление несколькими
персонажами не потребовало от движка ничего.

Из разделения сразу вылезли две вещи, которых слияние не показывало:

**Столкновения считаются вокруг тела, видимость — вокруг камеры.** В
третьем лице камера регулярно оказывается в другом секторе, чем персонаж:
он уже прошёл проём, а она ещё нет. Поэтому в `demo/main.c` вызовы
разные:

```c
	nsolids = solids_around(g, g->unit[g->controlled].pos, near, 64);
	...
	nsectors = wld_Visible(&g->world,
	    wld_SectorAt(&g->world, g->cam.pos), viewproj, sectors, 16);
```

Со слитой переменной эта разница не выражается вообще.

**Камера обновляется после подопечных.** Иначе она весь кадр показывает
вчерашнее положение, и картинка запаздывает на один шаг. В `game_step`
цикл по юнитам стоит раньше `cam_Update`, и это не случайный порядок.

В `test/test.c` на это есть проверка `test_camera_is_not_the_body`: тело в
одной комнате, камера в другой, и видно, что `wld_SolidsNear` и
`wld_Visible` отвечают про разные секторы. Тест нужен не движку, а тому,
кто будет читать демку как образец.

`yaw` и `pitch` есть и у камеры, и у юнита, и это разные углы: у камеры —
куда смотрит игрок, у юнита — куда развёрнута модель. Второй считается из
направления движения:

```c
	if (v3_len(wish) > 0.01f)
		u->yaw = atan2f(wish.x, -wish.z);
```

## Пул памяти

```c
static char pool[48 * 1024 * 1024];
```

48 мегабайт, выделенных на этапе компиляции. Это вся память, которую игра
когда-либо возьмёт. Из неё режут и текстуры, и модели, и временные буферы
загрузчиков.

Почему не `malloc`: смотри главу 04. Коротко — статический массив
исключает целый класс ошибок, а его размер видно в `ls -l` бинарника.

## `game_init`: загрузка

Хук вызывается, когда окно уже открыто и OpenGL уже работает. Это важно:
`gfx_MakeTexture` не может быть вызван раньше, чем создан контекст.

### Текстура

```c
	mark = arena_Mark(&g->mem);
	bytes = slurp(&g->mem, "demo/freebsd.tga", &len);
	if (bytes != 0 && tga_Probe(bytes, len)) {
		geo = tga_Geo(bytes);
		pixels = arena_Alloc(&g->mem, tga_CanvasBytes(bytes), 4);
		if (pixels != 0 &&
		    tga_Decode(pixels, tga_CanvasBytes(bytes), bytes, len) == 0)
			g->wall_tex = gfx_MakeTexture(pixels, geo, 1, 1);
	}
	arena_Reset(&g->mem, mark);
```

Читается так:

1. `arena_Mark` запоминает, сколько памяти занято сейчас.
2. `slurp` читает файл в арену. Это **функция игры**, а не движка, и она
   тут же ниже в файле — обычный `fopen`/`fread`. Движок файлов не
   открывает.
3. `tga_Probe` отвечает, можем ли мы вообще этот файл разобрать.
4. `tga_Geo` возвращает геометрию: ширина, высота, размер пикселя,
   упакованные в одно число (глава 07).
5. `tga_CanvasBytes` говорит, сколько байт займут распакованные пиксели,
   и мы берём столько из арены.
6. `tga_Decode` распаковывает.
7. `gfx_MakeTexture` отдаёт пиксели видеокарте и возвращает дескриптор.
8. `arena_Reset` откатывает арену к отметке — и файл, и распакованные
   пиксели исчезают одной строкой.

Восьмой шаг — вся суть арены. После того как пиксели скопированы в
видеопамять, они нам больше не нужны, и мы выбрасываем их без единого
`free()`.

Аргументы `gfx_MakeTexture(pixels, geo, 1, 1)` — сглаживание и повтор.
Сглаживание (`GL_LINEAR`) размывает текстуру при приближении; ноль даст
жёсткие квадратные пиксели, как на первой PlayStation. Повтор
(`GL_REPEAT`) позволяет координате текстуры выйти за единицу и начать
сначала — это то, чем на стену кладут одну плитку четыре раза.

### Модель

```c
	bytes = slurp(&g->mem, "demo/freebsd.obj", &len);
	if (bytes != 0 && obj_Parse(&g->model, bytes, len, &g->mem) == 0) {
		g->model_mesh = gfx_MakeMesh(g->model.verts, g->model.nverts,
		    g->model.index, g->model.nindex, 0);
	}
```

Здесь `arena_Reset` нет. Разница принципиальная: пиксели после загрузки в
видеокарту не нужны, а вершины нужны — по ним считаются попадания
(`coll_RayMesh`) и в них пишется анимация (`anim_Sample`). Видеопамять
читать нельзя, поэтому копия на стороне процессора остаётся.

Последний аргумент `gfx_MakeMesh` — «динамический ли меш». Ноль значит, что
вершины больше не изменятся, и драйвер может положить их в самую быструю
память. Для анимированной модели там стоит единица.

### Уровень

```c
	room(&b, -8.0f, -8.0f, 8.0f, 8.0f, 4.0f, 1);
	room(&b, -8.0f, 8.0f, 8.0f, 24.0f, 4.0f, 0);
	g->room_mesh = gfx_MakeMesh(b.v, b.nv, b.i, b.ni, 0);
```

Комнаты построены кодом, а не загружены. Функция `room()` в том же файле
складывает шесть четырёхугольников (пол, потолок, четыре стены), пропуская
одну стену там, где дверь. Настоящая игра загрузила бы сюда два `.obj`, и
движок не заметил бы разницы: на выходе всё равно массив вершин и массив
индексов.

Дальше уровень описывается движку:

```c
	here = wld_AddSector(&g->world, box(...), g->room_mesh, g->wall_tex);
	wld_AddSolid(&g->world, here, box(-1.5f, 0.0f, -1.5f, 1.5f, 1.0f, 1.5f));
	...
	wld_AddPortal(&g->world, here, there, a, b, c, d);
	wld_AddPortal(&g->world, there, here, b, a, d, c);
```

Сектор — это «комната»: что рисовать и в каких границах. Солид — коробка,
сквозь которую нельзя пройти. Портал — дверной проём: четырёхугольник, за
которым виден другой сектор. Порталы односторонние, поэтому их два. Всё
это подробно в главе 09.

### Первичная настройка сцены

```c
	gfx_SetLight(v3(-0.5f, -1.0f, -0.3f), 0.35f);
	gfx_SetFog(0.05f, 0.06f, 0.08f, 12.0f, 40.0f);
```

Свет здесь один и он направленный: у него нет позиции, только направление,
как у солнца. `0.35` — фоновая подсветка, чтобы неосвещённая сторона не
была абсолютно чёрной.

Туман задан цветом и двумя расстояниями: с 12 метров начинает
подмешиваться, к 40 закрывает полностью. Цвет тумана обязан совпадать с
цветом фона в `gfx_BeginFrame`, иначе на границе дальности будет видна
ступенька.

## Что происходит внутри `app_Run` до первого кадра

Порядок в `core/app.c` жёсткий, и почти каждый шаг зависит от предыдущего:

```
plat_Init()          соединиться с X-сервером, загрузить libGL
plat_OpenWindow()    создать окно и контекст OpenGL
gfx_Init()           загрузить точки входа GL, собрать шейдер
plat_AudioOpen()     попробовать открыть звук (может не выйти, это не ошибка)
snd_Init()           настроить микшер на частоту устройства
hooks->init()        тут просыпается игра
```

Если `gfx_Init` не сработал (например, шейдер не собрался), `app_Run`
закрывает окно и возвращает 1, а хук `init` не вызывается вообще. Игре не
приходится думать о полусломанном состоянии.

Если не открылся звук — это не ошибка, игра идёт молча. Отсутствие
звуковой карты не повод не запускаться.

## Итог главы

```
main()
 └─ app_Run(hooks)
     ├─ plat_Init / plat_OpenWindow / gfx_Init / plat_AudioOpen
     ├─ hooks->init(user)          ← game_init: ресурсы и уровень
     └─ пока не вышли:
         ├─ plat_Poll(&input)
         ├─ hooks->step(user, 1/60) × сколько накопилось
         ├─ hooks->draw(user, alpha)
         ├─ plat_Swap()
         └─ snd_Mix + plat_AudioWrite
```

Следующая глава разбирает этот цикл по строкам.
