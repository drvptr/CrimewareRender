# 03. Главный цикл

Файл `core/app.c`. Полсотни строк, в которых спрятана большая часть
неочевидных решений во всём движке.

## Наивный цикл и почему он плох

Самый очевидный игровой цикл выглядит так:

```c
while (running) {
	double now = time();
	float dt = now - previous;
	previous = now;

	poll_input();
	step(dt);        /* подвинуть всё на прошедшее время */
	draw();
}
```

Он работает и даже выглядит правильным: считаем, сколько прошло, столько и
двигаем. Ломается он тремя способами.

**Прыжок разной высоты.** Гравитация обычно пишется как
`velocity.y -= 18 * dt`, а позиция как `pos.y += velocity.y * dt`. Это
численное интегрирование, и его ошибка зависит от размера шага. На 30 FPS
прыжок выйдет заметно другой высоты, чем на 300. Игрок этого не поймёт, но
почувствует.

**Туннелирование.** Просадка до 5 кадров в секунду даёт `dt = 0.2`. Пуля,
летящая 100 м/с, за один шаг перепрыгнет 20 метров и пройдёт сквозь стену,
потому что проверка столкновения смотрит на отрезок, а не на все точки
внутри него.

**Невоспроизводимость.** Один и тот же ввод даёт разный результат на
разных машинах и даже в двух запусках подряд. Отладить такую ошибку
нельзя: она не повторяется.

## Что делаем вместо

```c
while (running) {
	now = plat_Time();
	behind += now - previous;
	previous = now;

	plat_Poll(&input);

	steps = 0;
	while (behind >= step && steps < 5) {
		h->step(h->user, step);
		behind -= step;
		steps++;
	}

	h->draw(h->user, (float)(behind / (double)step));
	plat_Swap();
	push_audio();
}
```

`step` — константа, `1.0f / 60.0f`. Логика получает всегда ровно её,
сколько бы времени ни занял кадр. Реальное время копится в `behind`, и цикл
внутри цикла отрабатывает столько шагов, сколько накопилось.

Разберём на числах. Шаг 16.67 мс, кадр занял 20 мс:

```
кадр 1: behind = 20.0   → один шаг, behind = 3.3
кадр 2: behind = 23.3   → один шаг, behind = 6.6
кадр 3: behind = 26.6   → один шаг, behind = 9.9
кадр 4: behind = 29.9   → один шаг, behind = 13.2
кадр 5: behind = 33.2   → два шага, behind = -0.1 → 0
```

Пять кадров, шесть шагов логики. За 100 мс реального времени прошло 100 мс
игрового, а каждый отдельный шаг был ровно 16.67 мс.

## Ограничение догона

```c
	steps = 0;
	while (behind >= (double)step && steps < 5) {
		...
	}
	if (behind > (double)step * 5.0)
		behind = 0.0;
```

Условие `steps < 5` — защита от «спирали смерти». Представь, что программа
встала на пять секунд: сработал брейкпоинт, система ушла в своп, ноутбук
закрыли. `behind` станет 5.0, и цикл попробует сделать 300 шагов логики
подряд. Эти 300 шагов займут больше времени, чем те пять секунд, за которые
они накопились, значит после них `behind` вырастет ещё сильнее, и игра
уже никогда не догонит.

Поэтому: не больше пяти шагов за кадр, а если отставание всё равно
чудовищное — обнулить его и считать, что этого времени не было. Игрок
увидит, что мир «прыгнул», и это правильное поведение: лучше прыжок, чем
вечное замедление.

## `alpha`: зачем `draw` получает дробь

```c
	h->draw(h->user, (float)(behind / (double)step));
```

После шагов в `behind` остаётся хвост: время, которое уже прошло, но на
целый шаг не набралось. `alpha` — этот хвост в долях шага, число от 0 до 1.

Смысл такой: логика знает позицию объекта в момент последнего шага, но с
тех пор прошло `alpha` шага, и честно рисовать надо чуть впереди. Если
хранить предыдущую и текущую позицию, картинка получается гладкой при любом
FPS:

```c
struct vec3 shown = v3_add(previous_position,
    v3_scale(v3_sub(current_position, previous_position), alpha));
```

В демо это не сделано, `alpha` игнорируется — при 250 FPS и шаге 60 Гц
разница не видна. Как только шаг станет 20 или 30 Гц, интерполяция
понадобится. Место, где её добавлять, — `game_draw`, а не движок: движок
не знает, какие у игры бывают позиции.

## Звук в том же цикле

```c
static void
push_audio(void)
{
	int room;

	room = plat_AudioSpace();
	if (room <= 0)
		return;
	if (room > AUDIO_SCRATCH_FRAMES)
		room = AUDIO_SCRATCH_FRAMES;
	snd_Mix(audio_scratch, room);
	plat_AudioWrite(audio_scratch, room);
}
```

Обычно звук делают через колбэк: драйвер сам будит твою функцию в
отдельном потоке, когда ему нужны данные. Тогда нужен поток, мьютекс на
список голосов и осторожность со всем, что микшер трогает.

Здесь модель обратная (push): спрашиваем у устройства, сколько влезет,
микшируем ровно столько, отдаём. Всё в главном потоке, никаких блокировок,
микшер можно отлаживать обычным отладчиком.

Плата: задержка звука привязана к длине кадра. При 60 FPS это порядка 16 мс
поверх буфера устройства, для игры незаметно. Для музыкального софта так
делать нельзя, для игры — можно.

`audio_scratch` — статический буфер на 8192 кадра. Он статический, а не из
арены, потому что нужен всегда и одного размера. Арена — для того, что
приходит и уходит.

## Ограничение частоты кадров

```c
	if (h->max_fps > 0) {
		budget = 1.0 / (double)h->max_fps;
		now = plat_Time();
		if (now - frame_start < budget)
			plat_Sleep(budget - (now - frame_start));
	}
```

Без этого пустая сцена будет рисоваться десять тысяч раз в секунду,
греть видеокарту и жечь батарею впустую. `max_fps = 250` в демо: заметно
выше любой развёртки, но не бесконечность.

Правильнее было бы включить вертикальную синхронизацию (`glXSwapInterval`),
и тогда `plat_Swap` сам ждал бы обновления монитора. Этого пока нет; в
списке дел.

## Что делает `plat_Poll` до шагов

```c
	plat_Poll(&input);
	if (input.quit)
		running = 0;
	if (input.resized)
		gfx_Viewport(input.width, input.height);
```

Опрос ввода стоит один раз за кадр, перед всеми шагами логики. Значит, если
за кадр случилось два шага, оба увидят одно и то же состояние клавиатуры.
Это правильно: события уже произошли, их порядок внутри кадра всё равно
неизвестен.

Тонкость с `hit`. В структуре ввода три массива:

```c
unsigned char hold[PLAT_KEYS];   /* клавиша нажата прямо сейчас */
unsigned char hit[PLAT_KEYS];    /* нажали в этом опросе */
unsigned char rel[PLAT_KEYS];    /* отпустили в этом опросе */
```

`hold` — для движения: пока держишь W, идёшь. `hit` — для действий: выстрел,
открыть дверь, пауза. Если проверять выстрел через `hold`, за один зажим
получится очередь из шестидесяти выстрелов в секунду.

`hit` и `rel` очищаются в начале каждого `plat_Poll`, то есть живут ровно
один кадр. Если за кадр случилось два шага логики, оба увидят `hit`, и
выстрелов будет два. Для 60 Гц против 250 FPS это невозможно (шагов всегда
не больше одного за кадр), но при 30 Гц шаге стоит помнить.

## Про epoll

Отдельно, потому что вопрос напрашивается: почему цикл не построен на
`epoll`, как сетевой сервер.

`epoll_wait` отвечает на вопрос «какой из моих файловых дескрипторов
готов» и засыпает, пока не готов ни один. Игровой цикл обязан работать,
когда не готов **никто**: мир движется, пока игрок стоит и ничего не
нажимает. Соединение с X-сервером — это действительно сокет, и его можно
отдать epoll, но таймер на конец кадра всё равно нужен, а с таймером epoll
не делает ничего сверх того, что уже делает неблокирующий разбор очереди
событий. Зато привязывает к Linux: во FreeBSD это `kqueue`, в Windows —
совсем другая история.

Он окупается ровно в одном случае: когда появится сеть. Тогда правильная
форма — `epoll_wait` с таймаутом, равным остатку кадра, и это правка одной
функции в `plat/`, а не переделка архитектуры.

## Измерение

```c
	frames++;
	if (now - fps_clock >= 0.5) {
		measured_fps = (float)((double)frames / (now - fps_clock));
		frames = 0;
		fps_clock = now;
	}
```

Считаем кадры за полсекунды и делим. Не мгновенное значение (оно скачет и
ни о чём не говорит), не среднее за всё время (оно не реагирует на
изменения). Достаётся через `app_Fps()`.

Второй счётчик — `gfx_DrawCalls()`, сколько вызовов отрисовки ушло за
последний кадр. Он полезнее FPS: если при повороте спиной к дверному
проёму число не падает, значит портальный граф собран неправильно, и это
видно сразу, без профайлера.
